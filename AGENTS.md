- Access Control Center (src/lib/access-control-model.ts) is a read-only projection of existing auth facts; enforcement never imports it — why: Stage 1 must not change authority.
- Canonical authorization lives in src/lib/authorize.ts (authorize(facts, permission, resource) → structured decision); access writes go only through src/lib/access-admin.functions.ts with escalation checks and append-only access_audit_events — why: one future authority, auditable changes; legacy checks stay until Stage 3 migrates them.
- Stage 3 cutovers must run through src/lib/authz-shadow.server.ts (shadowAuthorize) first; it always returns the legacy decision and logs payload-free categories to authz_shadow_events — why: canonical RBAC must never override legacy enforcement before cutover.
- Atomic Client/Fund permissions live in src/lib/atomic-permissions.ts; broad keys imply only non-destructive atomics, lifecycle/destructive atomics need explicit grant — why: create/edit must never imply archive/close/delete.
- Compliance & Controls (src/lib/compliance-model.ts, compliance-controls.functions.ts) uses append-only compliance_* tables reachable only via server fns gated by administration.* atomic permissions — why: evidence must be tamper-evident and never client-readable.
- Privileged Harmonious roles require an explicit, append-only account classification of Individual (src/lib/account-classification.ts; DB trigger re-checks) — why: shared/integration accounts must never hold admin authority.
- Canonical investment readiness lives in src/lib/investment-readiness.ts (pure projection); readiness views are read-only and investment_readiness_events/tasks are written only by reconcileInvestmentReadiness (after mutations, provider webhooks, or staff reconciliation) — why: page views must never change operational state.
- View As lives in src/lib/view-as.server.ts: a server-only, session-bound, read-only perspective (view_as_sessions) that re-checks staff + canonical relationship each call and renders converted screens through the subject's own server authorization; never token substitution — why: see what clients see without account takeover or elevation.
- Edit-as-Harmonious context (activeEditContext in src/lib/view-as.server.ts) is display-only, server-revalidated each call, auto-closed when stale, and never consulted by save paths — why: the banner must never grant permission or attribute edits to the client.
- Fund Investor Onboarding Links (src/lib/fund-onboarding-link*.ts) are opaque 256-bit tokens, service-role-only, one current link per offering; they only enter the existing startOnboarding flow (idempotent, unique open unprofiled onboarding) and expose only fund display name + manager before sign-in — why: one onboarding model, no enumeration or pre-auth data exposure.
- Manual investor entry (src/lib/investor-record*.ts) writes only canonical persons/investment_profiles/investor_onboardings, which may exist before sign-in (user ids nullable, person_id required) and are claimed on verified-email sign-in; every material change logs append-only investor_record_changes and non-authoritative values go to investor_record_suggestions — why: one investor model, provenance, no silent overwrite.
- Harmonious MSA/SOW status is a non-blocking projection (src/lib/commercial-agreement-model.ts, commercial-agreements.*); clients.contract_structure is staff-set, never inferred, and never feeds readiness or gates fund/investor work — why: an unsigned Harmonious agreement is a follow-up item, not an operational blocker.
- Related persons (owners/signers) are created only via src/lib/related-person.server.ts: always a new unclaimed Person, and any possible existing match opens a related_person_reviews item resolved explicitly by staff (re-points the relationship; never merges/deletes) — why: no silent Person reuse or candidate exposure to managers/investors.
- Canonical fund Legal Name is offerings.legal_entity_name, changed only via changeLegalName in src/lib/fund-setup-canonical.server.ts; history is append-only in offering_legal_name_history (DB trigger); fund_setups.legal_fund_name is deprecated — why: enter once, never rewrite history.
- Fund Setup section status lives in src/lib/fund-setup-canonical.ts (pure) and is separate from investment readiness; economics/classes reuse versioned fund_economics_versions with maker-checker — why: no second economics model.
- Investor funding does not check the Harmonious SOW (assertFundConditions returns early for "funding") — why: user decision; the SOW is commercial, not a funding control.
- Offering Documents (src/lib/offering-document-model.ts, offering-document-setup.server.ts) keep only metadata/versions/usage/applicability/signing config per version; uploads append versions, activation is explicit with Investor Impact, and execution stays per Investment — why: the uploaded file is authoritative and signed investors never move versions.
- SS-4 Responsible Party SSN/ITIN lives only in private.offering_responsible_party_identifiers (canonical AES-GCM tax-ID key, service-role RPCs via src/lib/responsible-party-identifier.server.ts); a DB trigger rejects plaintext in ss4 JSON and only SS-4 generation decrypts — why: sensitive identifiers need the encrypted boundary, not just authorization.
- Fund identity & investor record sync live in src/lib/fund-integrity.ts (pure) + fund-integrity.server.ts: normalized Fund names are unique via DB trigger (advisory-locked), renames append to offering_name_history, and Investor Records Sync only writes idempotent fund_record_sync_items resolved one-by-one through canonical services — why: sync is reconciliation, never import or silent overwrite.
- Fund duplicate resolution lives in src/lib/fund-duplicate-resolution.ts (pure) + .server.ts; consolidation only via the transactional consolidate_duplicate_fund RPC after an explicit Harmonious canonical choice, leaving append-only fund_aliases/fund_consolidation_moves and a retired (never deleted) Fund — why: no automatic merges, full provenance, all-or-nothing moves.
- Diligence Room documents are archived (diligence_documents.archived_at), never hard-deleted, and Box files are kept — why: preserve historical records; destruction needs a separate retention workflow.
- Person matching goes only through src/lib/person-resolution.ts (+ .server.ts, with person_creation_locks); Signature status only through src/lib/document-execution-status.ts; Funded only through src/lib/funding-status.ts; next-action wording through src/lib/readiness-reasons.ts — why: one concept, one rule, many views (Phase 3.8).
- Fund commercial terms live in append-only fund_pricing_snapshots (src/lib/commercial-pricing.ts pure + .server.ts), recorded automatically at Fund creation; below-baseline prices open pricing_approval_requests decided only by sales_management/super_admin, never the requester; commercial states never feed readiness or gate Fund/investor work — why: Fund creation is the SOW approval event and commercial follow-up must never block operations.
- Harmonious staff teams are a compatibility map over legacy roles (src/lib/harmonious-staff.ts); Sales roles get commercial access only and are not Operations staff — why: consolidate Operations/Administration without any role migration or access change.
- Harmonious Team ownership lives in src/lib/harmonious-team.ts (pure) + .server/.functions: Client assignments, Fund overrides only (inherit otherwise), append-only team_assignment_events; assignment never grants access or blocks work — why: change once at Client, routing ≠ authorization.
- Sales Overview (src/lib/sales-performance.functions.ts) is read-only and shows Sales investor name/stage/amount only — never email, tax, identity, KYC, bank or compliance data — why: user approved Sales pipeline visibility at that scope.
- Client Expected Services live in src/lib/service-packages.ts (pure packages/entitlements, prices only from the rate card) + client-service-config.functions.ts (append-only versioned client_service_configurations); Funds copy a chosen subset into fund_pricing_snapshots.service_config; Primary Contact is a designation on client_contacts (matched via Person Resolution, removed contacts deactivated) — why: one pricing chain, no duplicate people, client changes never rewrite Fund history.
